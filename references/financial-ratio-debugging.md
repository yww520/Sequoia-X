# 财报比率 / 金融数据管道的排查方法论

从修 `stock-valuation-lite` 排雷引擎的 3 个 bug 里提炼的通用套路。
适用于**任何**「原始财报 → 计算比率 → 出结论」的管道（排雷引擎、选股因子、
风控指标、回测信号）。

## 一、最高信号：结论的「分布形状」不合理

单只股票算出异常值，可能是公司真有问题。但**一整批同类标的得出同一个极端结论**，
几乎一定是管道 bug：

| 观察到的形状 | 优先怀疑 |
|---|---|
| 某行业**全部**成员触发同一条高危规则 | 字段名错 / 口径不一致（本次命中） |
| 某行业**全部**成员都满分通过 | 该字段根本没取到值、恒为默认值 |
| 比率恒为 `0.00` / `1.00` / `None` | 字段名错（取不到 → 落到 `or 0.0` 兜底） |
| 全市场比率分布极窄（如都挤在 0.9~1.1） | 分子分母用了同一个量 |
| 结论随报告期**无规律跳变** | 取错期次（列表顺序假设错） |

**行动**：先抽样手算 3~5 只，比对引擎输出。全部对不上就去找字段/口径，别去质疑业务规则。

## 二、查任何比率异常，先问这三件事

按顺序问，本次 3 个 bug 恰好各命中一问：

1. **分母是「时点」还是「期间」？**
   资产负债表科目（应收/存货/固定资产）是**时点余额**；
   利润表/现金流量表科目（营收/净利/经营现金流）是**期间流量**。
   余额 ÷ 流量必须先统一口径，否则量纲就是错的。

2. **分母是「累计」还是「单季」？**
   A 股财报的 `TOTAL_OPERATE_INCOME` 等字段通常是**年初至今累计**
   （Q1 三个月、中报六个月、三季报九个月、年报十二个月），**不是单季**。
   用中报累计数当分母，会把比率**高估约 2 倍**；用三季报高估约 1.33 倍。

   年化因子：`{3月: ×4, 6月: ×2, 9月: ×4/3, 12月: ×1}`

   > ⚠️ 注意：比率类规则（如「应收/营收 > 30%」）的**业务语义**是按年化口径定义的
   （规则文档里常写「全年累计」）—— 去找规则原文确认，别凭感觉。

3. **列表是「新→旧」还是「旧→新」？**
   财报 API 返回的列表顺序**不统一**：东财接口常是**最新期在前**（取 `[0]` 才是最新），
   而有些本地预解析管道是**旧→新**（取 `[-1]`）。
   **同一个文件里两种顺序并存**是常见坑 —— 用 `reversed()` 之后索引就反了。
   防御：不要靠索引猜，**读数据自带的日期字段**（`REPORT_DATE` / `periods`）。

## 三、反推技巧：从「错误输出」算出「引擎实际用了什么」

报错信息不明确时，用输出值**反解**内部参数，比读代码快：

```
引擎输出 36%，已知真实应收 20.79 亿
→ 反推分母 = 20.79 / 0.36 = 57.75 亿
→ 57.75 / 43.30 (真实 H1 营收) = 1.334
→ 1.334 ≈ 4/3 → 说明取到的月份 = 9 月，而不是真实的 6 月
→ 定位：报告期取值取到了老数据
```

这个手法（**输出 ÷ 已知真值 = 实际用的参数**）在调任何数值管道时都好用，
能直接指出「用错了哪一档因子 / 哪一期 / 哪个单位」。

## 四、字段名核对（最省时间的一步）

**先 dump 一期的完整字段列表，再写提取代码**，不要凭字段名语感硬猜：

```python
for k in list(d[0].keys()):
    print(k, '=', d[0][k])
```

本次踩的坑：代码找 `GOODS_SALE_SERVICE` / `SALE_GOODS_SERVICE`，
**实际字段是 `SALES_SERVICES`** —— 语感极像，但就是取不到，静默落到 `0.0`。
提取字段时**保留多个候选名兜底**，并把最可能命中的放最前：

```python
d.get("SALES_SERVICES") or d.get("GOODS_SALE_SERVICE") or d.get("SALE_GOODS_SERVICE") or 0.0
```

## 五、静默兜底是 bug 的放大器

`float(d.get("X") or 0.0)` 这类写法会把「字段不存在」变成「值为 0」，
再参与计算就产生**看起来合理的错误结论**（收现比 0.00 → 判「款项全被拖欠」）。

**防御模式**：对关键字段做**存在性断言**，缺失就跳过该规则或标记
`status="unknown"`，而不是当成 0 参与判定。区分「真的为 0」和「没取到」。

## 六、给他人项目改 bug 的边界

修别人的代码时（本次是 `~/stock-valuation-lite`，与 Sequoia-X 是独立项目）：

1. **改前备份**：`cp <file> /tmp/<file>.bak`
2. **只修能确证根因的**：有原始数据佐证、能复现、能验证修复效果
3. **不确定的一律不动**：字段名对不上但不知道正确替代名 → 不瞎猜
4. **业务判断交回用户**：如「两条规则是否重复」属于产品决策，不擅自删
5. **改完必须重启服务**：FastAPI 默认无热重载，不重启 = 没改
6. **用本地直调验证，而非反复打 HTTP**：
   ```bash
   ./venv/bin/python -c "import sys; sys.path.insert(0,'backend')
   from caibao_audit_engine import CaibaoAuditEngine as E
   fin = E.fetch_eastmoney_financials('002815.SZ')
   print(E.audit_stock({'meta':{...}, 'data':fin}))"
   ```
7. **汇报时说明「修了什么 / 故意没修什么 / 为什么」** —— 未修项要显式列出，
   否则用户以为都修好了
